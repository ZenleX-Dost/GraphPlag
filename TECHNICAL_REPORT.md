## 1. Executive Summary

GraphPlag is a state-of-the-art, distributed plagiarism detection system designed to identify semantic similarities and AI-generated content across massive document corpora. Unlike traditional lexical matching systems, GraphPlag leverages semantic graph representations (Syntactic Dependency Graphs) and Graph Neural Networks (GNNs) to detect paraphrased content and cross-lingual plagiarism with high accuracy.

The system has been re-architected from a monolithic research prototype into a scalable, cloud-native distributed system capable of indexing and searching over 10 million documents with sub-second query latency. By utilizing a microservices architecture orchestrated via Kubernetes, GraphPlag ensures high availability (99.9%), horizontal scalability, and fault tolerance. This report details the technical architecture, underlying technologies, distributed system patterns, and operational specifications of the GraphPlag platform.

## 2. System Overview

### 2.1 Application Purpose & Domain
**Domain:** Academic and Professional Integrity / Natural Language Processing (NLP)  
**Purpose:** To provide a robust, scalable solution for detecting plagiarism and AI-generated text (e.g., ChatGPT, Claude) in academic papers, legal documents, and code repositories. The system addresses the limitations of keyword-based matching by understanding the *meaning* and *structure* of sentences through graph-based analysis.

### 2.2 High-Level Architecture
GraphPlag follows a **Three-Tier Distributed Microservices Architecture**:

1.  **Tier 1: API Gateway & Ingestion Layer**
    *   Handles client requests, authentication, and document uploads.
    *   Acts as the entry point for the distributed processing pipeline.
2.  **Tier 2: Distributed Processing & Analysis Layer**
    *   Asynchronous task execution using a producer-consumer pattern.
    *   Dedicated workers for parsing, graph construction, embedding generation, and vector search.
    *   Utilizes Apache Spark for batch processing of large historical datasets.
3.  **Tier 3: Data Persistence & Indexing Layer**
    *   Polyglot persistence strategy using specialized data stores for relational data, vector embeddings, full-text indices, and caching.

### 2.3 Key Use Cases
*   **Real-time Document Analysis:** Users upload a document to receive an immediate plagiarism and AI probability report.
*   **Batch Corpus Indexing:** Institutions index millions of historical documents to build a reference database.
*   **Cross-Lingual Detection:** Detecting plagiarism where source text has been translated from another language.
*   **AI Content Verification:** verifying if a submitted text was generated by Large Language Models (LLMs).

## 3. Distributed System Functionalities

### 3.1 Scalability & Elasticity
*   **Horizontal Scaling:** The stateless API and Worker nodes can be scaled horizontally based on CPU utilization and queue depth. Kubernetes HPA (Horizontal Pod Autoscaler) manages replica counts (min: 3, max: 20).
*   **Database Sharding:** Elasticsearch indices are sharded (default: 5 shards) to distribute search load. Milvus vector database supports partitioning to handle 10M+ vectors.
*   **Async Processing:** Decoupling ingestion from processing via Redis queues allows the system to absorb traffic spikes without degradation.

### 3.2 Fault Tolerance & Resilience
*   **Retry Mechanisms:** Celery tasks are configured with automatic retries and exponential backoff for transient failures (e.g., network blips, database timeouts).
*   **Circuit Breakers:** Implemented in the API Gateway to prevent cascading failures when downstream services (e.g., Vector DB) are unresponsive.
*   **Dead Letter Queues (DLQ):** Failed tasks that exceed retry limits are moved to a DLQ in Redis for manual inspection, preventing data loss.
*   **Self-Healing:** Kubernetes liveness and readiness probes ensure unhealthy pods are automatically restarted.

### 3.3 Data Consistency & Replication
*   **Eventual Consistency:** The search indices (Milvus, Elasticsearch) are eventually consistent with the primary metadata store (PostgreSQL).
*   **Replication:**
    *   **PostgreSQL:** Uses Write-Ahead Logging (WAL) for streaming replication to read replicas.
    *   **Elasticsearch:** Configured with `number_of_replicas: 1` for high availability.
    *   **Redis:** Uses AOF (Append Only File) persistence and master-slave replication.

### 3.4 Inter-Process Communication (IPC)
*   **Synchronous (REST):** Client-to-API communication uses HTTP/2 over REST.
*   **Asynchronous (Message Queuing):** Internal service communication relies on Redis as a message broker for Celery.
*   **Data Streaming:** Server-Sent Events (SSE) are used to stream real-time analysis progress to the client.

### 3.5 Concurrency & Parallelism
*   **Task Parallelism:** Document processing is broken down into independent sub-tasks (Parsing, AI Detection, Vector Search) executed in parallel by different worker pools.
*   **Data Parallelism:** Apache Spark is used for batch processing, distributing the computation of graph kernels across a cluster of worker nodes.
*   **Async I/O:** FastAPI utilizes Python's `asyncio` to handle thousands of concurrent connections with non-blocking I/O.

### 3.6 State Management
*   **Stateless Services:** API and Worker nodes are stateless, storing all session data and job states in Redis.
*   **Distributed Cache:** Redis serves as a shared state store for job progress tracking, allowing any API instance to query the status of any job.

## 5. Technical Specifications & Performance Metrics

### 5.1 Performance & Latency
*   **Query Latency (10M docs):** < 4 seconds (p95)
*   **Vector Search Latency:** < 50ms
*   **Document Parsing Speed:** ~100ms per 1000 words
*   **Throughput:** Supports 100+ concurrent analysis requests per node.

### 5.2 Scalability Targets
*   **Document Capacity:** Tested up to 10 million documents; architected for 100M+.
*   **Concurrent Users:** 1000+ active users.
*   **Batch Processing:** Capable of indexing 1M documents in < 4 hours using Spark cluster.

### 5.3 Reliability & Availability (SLA)
*   **Uptime Target:** 99.9%
*   **RPO (Recovery Point Objective):** < 5 minutes (Async replication lag)
*   **RTO (Recovery Time Objective):** < 15 minutes (Automated K8s failover)

### 5.4 Resource Consumption (General Profile)
*   **API Node:** 2 vCPU, 4GB RAM
*   **Worker Node:** 4 vCPU, 8GB RAM (High CPU for parsing/inference)
*   **Vector DB Node:** 8 vCPU, 32GB RAM (Memory intensive for HNSW index)

### 5.5 Data Models (High-Level Conceptual)
*   **Document:** `{ id, content_hash, text, metadata, embedding_vector, created_at }`
*   **AnalysisJob:** `{ job_id, user_id, status, progress, result_summary, created_at }`
*   **Match:** `{ source_doc_id, target_doc_id, similarity_score, match_segments }`

### 5.6 API Specifications (Overview)
*   `POST /analyze`: Multipart/form-data upload. Returns `job_id`.
*   `GET /results/{job_id}`: Returns JSON stream of results.
*   `GET /status/{job_id}`: Returns `{ status: "processing", progress: 45 }`.

## 6. Architecture & Deployment Details

### 6.1 Deployment Topology
The system is deployed as a set of containerized services within a Virtual Private Cloud (VPC).
*   **Public Subnet:** Load Balancer, Ingress Controller.
*   **Private Subnet:** API Pods, Worker Pods.
*   **Data Subnet:** Databases (PostgreSQL, Milvus, Elastic, Redis) - No public access.

### 6.2 Infrastructure as Code (IaC)
Deployment is managed via Kubernetes manifests located in `k8s/`:
*   `deployment.yaml`: Defines stateless application sets.
*   `service.yaml`: Defines internal networking and LoadBalancers.
*   `autoscaling.yaml`: Defines HPA rules.

### 6.3 Environment Setup
*   **Development:** Docker Compose (`docker-compose-scalable.yml`) for one-click local replication of the prod stack.
*   **Production:** Kubernetes cluster with managed database services (AWS RDS, ElastiCache) recommended.

## 8. Future Considerations & Roadmap

### 8.1 Current Challenges
*   **Cold Start:** Initial loading of large ML models into memory can delay worker startup.

### 8.2 Planned Enhancements
